## 架构决策

### ADR-001：以 Termux 为运行基础

复用终端模拟器、终端界面、会话和命令执行能力；AI 首页与任务管理加入同一个 APK。保留上游可构建状态，先跑通基础环境，再改产品界面。

首先比较两条包名路线：保留 `com.termux` 以验证既有包环境，或使用独立包名并适配 bootstrap 和软件包路径。最终选择必须通过构建与真机验证后记录，不在规划阶段假设改包名无成本。若现有安装发生签名或数据冲突，先制定迁移方案，不自动卸载用户应用。

### ADR-002：本地 Agent，远程模型

手机维护任务状态、执行循环和历史。模型连接层先支持用户实际使用的一家 provider，后续扩展。模型负责决策，执行器返回可核验的结果；不把模型文本中的“完成”当成成功依据。

### ADR-003：脚本通过能力桥接操作手机

脚本运行环境、普通安卓进程、Shizuku 服务具有不同权限。统一能力桥接提供应用查询、启动、界面观察和动作执行；脚本可以动态调用和组合它们。

桥接仅供已授权的本地任务使用。每次调用关联任务身份、权限和超时，防止其他应用通过公开入口调用高权限能力。Shizuku 通道失效时返回明确错误，不默默声称执行成功。

### ADR-004：接口与界面操作结合

有明确系统或应用接口时直接调用；否则观察界面并执行点击、输入、滑动。界面结构不完整时再使用可用且获授权的屏幕图像。先执行一小步，再观察结果；不一次盲目执行长串坐标操作。

## 第一轮具体顺序

1. 提交文档，创建 P01–P05 对应 Issue（#1–#5）。
2. 在基础环境分支引入选定 Termux 源码，记录来源和构建命令。
3. 保持上游构建配置优先跑通，避免同时升级工具链、重写 UI 和改运行路径。
4. 生成可安装 APK，在用户手机验证 Shell 和一个数据处理脚本。
5. 加入最小能力验证页面，分别验证 Shizuku 与无障碍，不等待完整 AI 界面。
6. 用一段手写脚本调用手机能力验证桥接，再进入模型动态生成脚本阶段。

首轮目标是证明同一个 APK 能运行代码并操作手机。聊天外观、任务模板市场、多 provider 和持续后台运行不占用首轮工作量。

## 验证与发布约定

- 代码变更执行相关构建；涉及任务状态、取消或权限边界时补充有实际价值的自动验证。
- 手机权限、界面交互及厂商后台行为必须真机验证，模拟器或编译成功不能替代。
- 代表性任务记录输入、结果、耗时、重试和人工接手次数；报告实际数据，不预设成功率。
- 出现权限撤销、进程被杀、网络中断时保留失败状态；对发送、删除等动作先检查是否已经发生，再决定是否重试。
- PR 描述包含问题、修改、验证证据和未验证事项。私人使用版本的 APK 与提交关联；签名方案在首次持续安装前确定。
- 仓库存在后以 Issue 和代码提交记录进展，不将文档里的规划状态误写成已完成。
